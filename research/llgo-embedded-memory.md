# LLGo embedded targets and virtual-memory capabilities

English | [简体中文](llgo-embedded-memory.zh-CN.md)

Research date: 2026-11-16. The local checkout was found at `~/source/goplus/llgo`; its inspected revision is [`0f804925c56d9f756e5e4b25271662157799a05a`](https://github.com/cpunion/llgo/tree/0f804925c56d9f756e5e4b25271662157799a05a). This is a configuration and hardware-source review, without new board builds or hardware tests. The LLGo checkout was not modified.

**Most MCU families in these target profiles cannot provide transparent, general-purpose paged RAM through an OS or allocator alone.** Some profiles have limited external-memory translation; K210 has a nonstandard MMU; Cortex-A57 has a conventional MMU. Hardware capability, firmware configuration, runtime integration, and usable VM allocation APIs must be assessed separately.

## Scope of the target inventory

The inspected `targets/` contains 210 JSON profiles, including board aliases, CPU templates, configuration mixins, and five WebAssembly profiles. Recursively resolving parent CPU settings and build tags groups them as 142 Cortex-M, 18 AVR, 9 ESP32, 10 ESP32-C3, 3 ESP8266, 2 FE310, 2 K210, one each Game Boy Advance, TKey, Nintendo Switch, and RISC-V QEMU, plus 15 generic/mixin and five Wasm profiles. These counts are profiles, not distinct chips or verified working boards. [Target directory](https://github.com/cpunion/llgo/tree/0f804925c56d9f756e5e4b25271662157799a05a/targets)

The build script skips selected targets and treats some missing CPU/triple configurations as warnings. Merely finding a profile is insufficient evidence of working compiler, runtime, hardware, or VM support. Generic `riscv32`/`riscv64` names and LLVM feature strings do not determine a concrete chip's MMU. Likewise, a bare-metal profile using the `linux` build tag is not evidence that Linux or `mmap` is present. [Build coverage script](https://github.com/cpunion/llgo/blob/0f804925c56d9f756e5e4b25271662157799a05a/_demo/embed/targetsbuild/build.sh) · [Target inheritance](https://github.com/cpunion/llgo/blob/0f804925c56d9f756e5e4b25271662157799a05a/internal/targets/loader.go)

## Families without a general-purpose paging MMU

- **Cortex-M0/M0+/M3/M4/M7/M33:** the profiles include RP2040 and RP2350; nRF51/nRF52/nRF52833/nRF52840; SAMD21/SAMD51/SAME51/SAME54; the configured STM32 F1/F4/F7/L0/L4/L5/WL variants; and Teensy 3.6/4.0/4.1 using MK66/i.MX RT1062. Cortex-M memory protection, where implemented, does not supply CPU virtual-to-physical page translation. TrustZone also does not add it. This classification concerns general RAM paging, not every memory-window feature in the SoC. [Arm explanation](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/security-principles-for-trustzone-for-armv8_2d00_m-webinar) · [RP2040/RP2350 profiles](https://github.com/cpunion/llgo/tree/0f804925c56d9f756e5e4b25271662157799a05a/targets)
- **AVR ATmega/ATtiny:** configured chips are ATmega1280/1284P/2560/328P/328PB/32U4 and ATtiny85/1616, plus board aliases and the AVR emulator. Their native data-memory accesses are not backed by a general page-table MMU. [Representative ATmega328P memory architecture](https://ww1.microchip.com/downloads/en/DeviceDoc/Atmel-7810-Automotive-Microcontrollers-ATmega328P_Datasheet.pdf)
- **SiFive FE310 / HiFive1 Rev B:** the E31 supplies physical protection, not Sv32 virtual memory. The FE310-G002 manual describes M/U privilege modes and PMP in §§3.6–3.7. Generic RISC-V virtual-memory specifications do not imply that this implementation contains translation hardware. [SiFive manual](https://sifive.cdn.prismic.io/sifive/034760b5-ac6a-4b1c-911c-f4148bb2c4a5_fe310-g002-v1p5.pdf)
- **Game Boy Advance:** the configured ARM7TDMI platform does not have a general MMU. The name ARM7TDMI alone is not proof for every SoC: Arm also integrated that core into other products with added MMU hardware. [LLGo platform](https://github.com/cpunion/llgo/blob/0f804925c56d9f756e5e4b25271662157799a05a/targets/gameboy-advance.json) · [Arm processor feature comparison](https://documentation-service.arm.com/static/5ea04d399931941038de55af)
- **TKey:** its PicoRV32-derived FPGA CPU does not implement MMU instructions; the vendor also documents restricted CSR/privilege and interrupt facilities. Replacing the FPGA logic could add capabilities, subject to resources and substantial redesign, but installing a different OS does not do so. [TKey hardware handbook](https://dev.tillitis.se/castor/hw/)

RP2350 deserves an extra qualification: its QMI peripheral has eight XIP translation entries for 4 MiB windows, and the chip supports external PSRAM. These are limited external-memory windows, not a general SRAM page table. A specialized allocator could investigate them, but independent arbitrary page mapping and a complete demand-paged arena have not been established here. [Raspberry Pi QMI registers](https://github.com/raspberrypi/pico-sdk/blob/master/src/rp2350/hardware_structs/include/hardware/structs/qmi.h) · [Chip memory comparison](https://www.raspberrypi.com/documentation/microcontrollers/microcontroller-chips.html)

## Limited translation and full-MMU exceptions

**ESP32 is not accurately described as having no MMU.** ESP-IDF exposes external-memory mapping. On the original ESP32, Himem separates external PSRAM allocation from address-window allocation and maps/unmaps 32 KiB banks within a limited 4 MiB CPU window. This is relevant to a bounded reserve/map allocator using external RAM. It does not provide a large sparse address space over arbitrary internal SRAM. A bank cannot be remapped to unrelated data while valid users of its old mapping remain. Integration with LLGo and the required board PSRAM are untested here. [Himem](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/system/himem.html)

**ESP32-C3 also has an MMU for external mapping**, but the reviewed ESP-IDF mapping driver lists SPI flash as its physical target. That does not establish a writable RAM page-pool backend. ESP8266's documented “MMU” configuration concerns instruction RAM and external-flash cache allocation; it similarly does not establish general RAM paging. [ESP32-C3 mapping](https://docs.espressif.com/projects/esp-idf/en/stable/esp32c3/api-reference/system/mm.html) · [ESP8266 core documentation](https://github.com/esp8266/Arduino/blob/master/doc/mmu.rst)

**K210 / Maix Bit has an Sv39 MMU based on privileged-spec draft 1.9.** The reviewed Linux device tree explicitly says mainline does not support that draft and enables K210 only in the NOMMU case. A dedicated compatible runtime could investigate the existing hardware; this is not the same situation as adding absent hardware. Its MMU also does not imply LLGo currently enables or uses it. [Linux K210 description](https://github.com/torvalds/linux/blob/master/arch/riscv/boot/dts/canaan/k210.dtsi)

**Nintendo Switch's Cortex-A57 has a conventional MMU.** The target profile alone does not establish permission to alter mappings or a suitable VM API in its execution environment. **RISC-V QEMU `virt`** can emulate an MMU-capable CPU, but this is a virtual platform, not evidence about a physical MCU; the specific LLGo firmware would still need VM integration. Wasm profiles and generic templates should be assessed separately. [Cortex-A57 MMU](https://support.arm.com/documentation/ddi0488/c/memory-management-unit) · [QEMU virt](https://www.qemu.org/docs/master/system/riscv/virt.html)

## Can software, a third party, or new hardware supply it?

An OS on hardware with a suitable translation mechanism can implement page allocation, page tables, faults, and the reserve/map/discard interface. The OS may be minimal and need no swap device if it only discards dead data and keeps live demand within RAM. Page-table walking or TLB refill can itself be software-managed on suitable architectures; that still requires an access path capable of applying the translations. [RISC-V address translation and software refill](https://riscv.github.io/riscv-unified-db/manual/html/isa/isa_20240411/chapters/supervisor.html)

On hardware without that path, a software page table is just data. A native `load [address]` will not consult it. MPU/PMP faults can enforce protection, but handlers cannot make unsupported translation happen on a retried instruction. Emulating the instruction, copying data into a suitable existing physical window, or rewriting execution changes the mechanism and its costs.

Software simulation is possible in principle: a compiler can replace relevant accesses with translations through block/page tables, or an interpreter/emulator can translate guest accesses. A runtime can also represent references as handles with offsets. Translation checks can sometimes be hoisted or cached, but performance, ABI, raw pointer identity, C/assembly access, and DMA must be designed for that representation. This is an architectural option, not a measured LLGo optimization. [QEMU's distinct host-pointer and guest-virtual-address access paths](https://www.qemu.org/docs/master/devel/loads-stores.html)

Additional hardware can translate accesses only if placed on their actual memory path. An external SPI device cannot intercept ordinary accesses to an MCU's on-chip SRAM. A redesigned SoC, FPGA soft CPU, or suitable external-memory bus could include translation logic, but that is a hardware redesign limited to the accessible address paths, not an OS package that works on every existing board. TKey's FPGA makes this distinction particularly concrete; fitting a capable design in that FPGA is not established by this review.

For the proposed language, treat native VM, limited external-memory windows, and no-MMU storage as distinct capabilities. Use bounded or segmented arenas for the common MCU path; consider ESP32 PSRAM mapping as a targeted experiment. If software-translated references are explored, measure their cost separately from native pointer loads. The inspected LLGo bare-metal GC currently takes its heap boundaries from linker symbols, and its `gcGrowMemory` returns the old boundary; it is not an existing demand-paged allocator.
